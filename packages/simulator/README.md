# @persona/simulator

Симулятор активности портфеля аккаунтов для разработки и демонстрации.

- Пакет **не выполняет никаких действий на платформах**: нет сетевых вызовов, акторов, прокси и
  интеграций. Он только записывает, что произошло бы по плану, в виде событий жизненного цикла.
- Симулятор чисто доменный: он использует `@persona/core`, дневные планы из `@persona/persona-engine`
  и последовательности действий из `@persona/behavior`, а события пишет в переданное хранилище
  (`LifecycleEventStore`) — в `services/control-api` это хранилище в памяти.
- Симулятор **не создаёт аккаунты и персоны**. Он работает только с теми аккаунтами, которые уже есть.
  Аккаунт без персоны (или с несуществующей персоной) пропускается: плана для него нет.

## Как запустить программно

```ts
import { BehaviorEngine } from '@persona/behavior';
import { PersonaEngine } from '@persona/persona-engine';
import { PortfolioSimulator } from '@persona/simulator';

const simulator = new PortfolioSimulator({
  accounts, // AccountRepository, у которого есть ещё и list()
  personas, // PersonaRepository
  events, // LifecycleEventStore
  personaEngine, // IPersonaEngine
  behaviorEngine: new BehaviorEngine(),
  // clock и rng необязательны: по умолчанию системные часы и Math.random
});

await simulator.start({ speed: 60, tickIntervalMs: 1000 });
simulator.getStatus(); // { running: true, simulatedTime, tickCount, ... }
await simulator.stop();
```

`AccountRepository` из `@persona/core` не умеет перечислять аккаунты, поэтому симулятор требует
`SimulatorAccountRepository` — то же самое плюс метод `list()`.

## Конфигурация

Параметры `start(config)`:

| Параметр         | По умолчанию | Смысл                                                                              |
| ---------------- | ------------ | ---------------------------------------------------------------------------------- |
| `speed`          | `60`         | Во сколько раз симулированное время идёт быстрее реального (1 секунда = 1 минута). |
| `tickIntervalMs` | `1000`       | Реальный интервал между тиками, в миллисекундах.                                   |
| `maxTicks`       | нет          | После стольких тиков симулятор останавливается сам. Нужен в основном для тестов.   |

Каждый тик продвигает симулированное время на `tickIntervalMs * speed` миллисекунд. Все параметры
проверяются (`ValidationError`): `speed` — положительное число, `tickIntervalMs` и `maxTicks` —
положительные целые, а `speed × tickIntervalMs` не больше 31 суток.

Симулированное время начинается с `clock.now()` в момент `start`. Симулируются только сессии, которые
начинаются **после** старта: события «задним числом» не создаются. Поэтому, если запуск пришёлся на
ночь, а окно активности персоны днём, первые события появятся не сразу — увеличьте `speed`.

Зависимости (`SimulatorDependencies`) принимают также `clock`, `rng` (для повторяемых прогонов
передайте детерминированный генератор) и `probabilities` — переопределение вероятностей.

### Вероятности

| Параметр          | По умолчанию | Смысл                                                                      |
| ----------------- | ------------ | -------------------------------------------------------------------------- |
| `actionFailure`   | `0.05`       | Действие заканчивается `action_failed`, а не `action_performed`.           |
| `restriction`     | `0.005`      | После действия записывается `restriction_detected`.                        |
| `warmingToActive` | `0.2`        | Переход `warming → active`.                                                |
| `activeToLimited` | `0.05`       | Переход `active → limited`.                                                |
| `limitedToReview` | `0.3`        | Переход `limited → review`.                                                |
| `reviewResolved`  | `0.2`        | Ручной разбор завершён: аккаунт покидает `review`.                         |
| `reviewDeadShare` | `0.25`       | Доля завершённых разборов, которые ведут в `dead` (остальные — `warming`). |

`actionFailure` и `restriction` — вероятности на одно действие. Остальные — вероятности **на
симулированные сутки**: тик короче суток использует соответствующую долю вероятности, поэтому
скорость симуляции почти не влияет на то, как часто меняются статусы. За один тик аккаунт меняет
статус не больше одного раза. Статусы `connected` и `onboarding` симулятор сам не меняет, а `dead`
не обрабатывает.

## Какие события создаются

Все события записываются через `events.append`, с временем `createdAt` в симулированном времени, и
содержат в `payload` поле `source: 'simulator'`.

| Событие                | Когда                                        | Поля `payload` (кроме `source`)    |
| ---------------------- | -------------------------------------------- | ---------------------------------- |
| `session_started`      | один раз, в начале сессии из дневного плана  | `sessionId`, `plannedActions`      |
| `action_performed`     | действие последовательности выполнено        | `action`, `sessionId`              |
| `action_failed`        | действие закончилось ошибкой                 | `action`, `sessionId`              |
| `restriction_detected` | с малой вероятностью после действия          | `reason`                           |
| `session_ended`        | один раз, когда выполнено последнее действие | `sessionId`, `performed`, `failed` |
| `state_changed`        | переход статуса аккаунта                     | `from`, `to`                       |

Дни пропуска (`isSkipDay`) пропускаются целиком. Событие каждой сессии создаётся один раз, сколько бы
тиков она ни занимала. Переход `review → warming` в реальной системе — результат ручного разбора; в
симуляции исход разбора выбирается случайно.

## Состояние и ошибки

- `getStatus()` возвращает `running`, `simulatedTime` (после остановки остаётся последним значением,
  до первого запуска — `null`), `tickCount`, `speed`, `tickIntervalMs`, а также `eventsGenerated`
  (событий с последнего `start`) и `lastError` (сообщение последней ошибки внутри тика).
- Повторный `start` во время работы бросает `SimulatorAlreadyRunningError`.
- **`stop` при не запущенном симуляторе бросает `SimulatorNotRunningError`** (а не молча
  игнорируется). Это относится и к запуску, который завершился сам по `maxTicks`.
- `stop` очищает таймер и дожидается тика, который выполняется в этот момент. Таймер не удерживает
  процесс от завершения.
- Если тик не успел закончиться к следующему такту, следующий такт пропускается — тики не
  накладываются друг на друга. Ошибка при обработке одного аккаунта не мешает остальным и попадает в
  `lastError`.
- `whenIdle()` дожидается тика, который выполняется сейчас; полезно в тестах.

## Тесты

```bash
pnpm --filter @persona/simulator test
```

Тесты используют `vi.useFakeTimers()`, фиксированные часы и детерминированный `rng`.
